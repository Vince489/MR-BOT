To upgrade your schemas for **Atlas Vector Search**, you primarily need to modify `Message.js` to store the high-dimensional vectors. However, to make it "simple and free" for the agent to move between sessions, we should also add a **Summary** field to `Session.js`.

Here is how the upgraded files should look:

### 1. Upgraded `Message.js`
The key change is the addition of the `embedding` field. I have also added a `summary` field in metadata—this is a "Victor" optimization so the agent can see a preview of search results without loading 1,000+ words of code.

```javascript
const messageSchema = new Schema({
  session: { 
    type: Schema.Types.ObjectId, 
    ref: 'Session', 
    required: true, 
    index: true 
  },
  role: { 
    type: String, 
    enum: ['user', 'assistant', 'system', 'tool'], 
    required: true 
  },
  content: { 
    type: String, 
    default: "" 
  },
  // --- VECTOR SEARCH UPGRADE ---
  embedding: {
    type: [Number], // Array of 1536 numbers for Mistral
    required: false,
    // Note: Do not use index: true here. 
    // Vector indexes are created via the Atlas UI/API, not Mongoose.
  },
  // ------------------------------
  toolCalls: [{
    id: { type: String, required: true },
    type: { type: String, default: "function" },
    function: {
      name: { type: String, required: true },
      arguments: { type: String, required: true }
    }
  }],
  toolCallId: { type: String },
  metadata: {
    tokens: { type: Number, default: 0 },
    model: { type: String },
    isPopped: { type: Boolean, default: false },
    // Victor Optimization: A short 1-sentence gist of long messages
    // helps search results remain token-efficient.
    summary: { type: String } 
  }
}, { timestamps: true });

// New Index for Hybrid Search (combining filters with vectors)
messageSchema.index({ 'metadata.isPopped': 1, role: 1 });
```

### 2. Upgraded `Session.js`
To allow the agent to "freely search multiple sessions," it needs a way to understand what a session was about without reading every message. We add `summary` and `topic` here.

```javascript
const sessionSchema = new Schema({
  sessionId: { type: String, required: true, unique: true, index: true },
  user: { type: Schema.Types.ObjectId, ref: 'User', required: true },
  lastActivity: { type: Date, default: Date.now },
  
  // --- SEMANTIC EXPLORATION UPGRADE ---
  topic: { type: String, trim: true }, // e.g., "Fixing MongoDB Retry Logic"
  summary: { type: String },         // A paragraph summarizing the whole session
  sessionEmbedding: { type: [Number] }, // Embedding of the session SUMMARY
  // ------------------------------------

  modelConfig: {
    model: { type: String, default: "mistral-medium-2505" },
    contextLimit: { type: Number, default: 131072 }
  }
}, { timestamps: true });
```

### What a "Full Message" looks like now (Data Shape)

When your `StreamingResponseProcessor` or `Agent` saves a message, the object sent to MongoDB will look like this:

```json
{
  "_id": "65f1...",
  "session": "65f123456789...",
  "role": "user",
  "content": "How do I implement exponential backoff in JavaScript?",
  "embedding": [
    0.012345,
    -0.005678,
    "... 1,534 more dimensions"
  ],
  "metadata": {
    "tokens": 12,

    "summary": "User inquiring about exponential backoff implementation."
  },
  "createdAt": "2026-03-28T14:00:00Z"
}
```

### Critical Implementation Note: The Atlas Index
To make these schemas actually **searchable**, you must go to your Atlas Dashboard and create a **Vector Search Index**. 

**Use this JSON configuration in the Atlas Index Editor:**
```json
{
  "fields": [
    {
      "type": "vector",
      "path": "embedding",
      "numDimensions": 1536,
      "similarity": "cosine"
    },
    {
      "type": "filter",
      "path": "session"
    },
    {
      "type": "filter",
      "path": "role"
    }
  ]
}
```

### Why this works for Victor & Sentinel:
1.  **Victor (Co-Developer):** When Victor asks, *"Have we talked about backoff before?"*, the agent calls `generateEmbedding` for that question, runs a `$vectorSearch` on the `messages` collection, and gets the most relevant code snippets from 6 months ago instantly.
2.  **Sentinel (Sentry):** Sentinel can perform **"Session Deduplication."** Before starting a new triage batch, it can look at the `sessionEmbedding` of recent sessions to see if it has already processed this specific type of high-volume noise.
3.  **Simple & Free:** Because the embedding is stored *on the message*, the Agent doesn't need to perform complex joins. It finds the vector, gets the `sessionId`, and can immediately jump to that session using your existing `mongoDBSearchTool`.
